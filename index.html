A social platform on async Python and hand-written SQL.

Vantage Point is an Instagram-style social app: feeds, follows, private accounts, media posts, comments, notifications. It was ported from a legacy PHP codebase to FastAPI and asyncpg. The original behavior is preserved, but the data layer was rebuilt as explicit, parameterized SQL against PostgreSQL, with no ORM between the code and the query plan.

01Overview

A faithful port first, a refactor second.

The source was a PHP application built around one "universal" class that handled sessions, the follow graph, private-account rules and online status. The goal was to keep that behavior exactly while moving to a typed, async Python stack, so the port went method by method. Logic that had to survive became small functions in app/universal.py. Persistence moved into per-domain query modules.

The app serves two surfaces from the same code: server-rendered Jinja2 pages for the browser and a JSON API validated by Pydantic. Both run through the same authentication dependency and the same SQL.

02Architecture

Every request takes the same short path.

A FastAPI router resolves two dependencies: a pooled asyncpg connection and the current user from a session token. It then calls a query function that holds the literal SQL. Nothing generates SQL at runtime, so every query in production can be read in the repository.

03Data model

Postgres does the integrity work.

The schema is built with nine numbered SQL migrations. The database enforces invariants itself: CHECK (follower_id <> followee_id) blocks self-follows, unique pairs stop duplicate follows, likes and blocks, CITEXT makes usernames case-insensitive, and an enum tracks follow state for private accounts.

04In the code

The home feed is one query.

The feed shows the viewer's own posts plus posts from accounts they follow with an accepted follow. That one condition is what keeps a private account's posts out of a pending follower's feed. Pagination is cursor-based, so deep pages cost the same as the first.

app/queries/posts.pylist_feed_posts
async def list_feed_posts(
    conn: asyncpg.Connection, viewer_id: int, limit: int, before: datetime | None,
) -> list[asyncpg.Record]:
    return await conn.fetch(
        POST_SELECT_SQL + """
        WHERE p.group_id IS NULL
          AND (p.author_id = $1 OR p.author_id IN (
              SELECT followee_id FROM follows WHERE follower_id = $1 AND status = 'accepted'
          ))
          AND ($3::timestamptz IS NULL OR p.created_at < $3)
        ORDER BY p.created_at DESC
        LIMIT $2
        """,
        viewer_id, limit, before,
    )
  1. Parameterized, never interpolated. Every value goes to Postgres as $n, which rules out SQL injection by construction.
  2. Keyset pagination. before is the last timestamp the client saw. No OFFSET scan, and no duplicate posts when new ones arrive mid-scroll.
  3. Index-backed. idx_follows_follower (follower_id, status) serves the subquery, and a partial index on posts (author_id, created_at DESC) WHERE deleted_at IS NULL serves the per-author lookups.

Following a private account is an idempotent upsert

app/queries/follows.pycreate_follow
status = "pending" if target_is_private else "accepted"
return await conn.fetchrow(
    """
    INSERT INTO follows (follower_id, followee_id, status)
    VALUES ($1, $2, $3)
    ON CONFLICT (follower_id, followee_id) DO UPDATE
        SET status = CASE WHEN follows.status = 'rejected'
                          THEN EXCLUDED.status ELSE follows.status END
    RETURNING id, follower_id, followee_id, status, created_at
    """,
    follower_id, followee_id, status,
)

A double-click or retry can't create a second row or overwrite an accepted follow. A rejected request can be re-sent. All of it happens in one round trip, with no read-then-write race.

05Decisions

Choices, and what they cost.

Data access

Raw SQL over an ORM

Queries are plain strings in app/queries/, run through asyncpg. Every query can be read, run with EXPLAIN and indexed on purpose. The cost is writing row mapping by hand, which Pydantic schemas handle at the API edge.

Auth

Session tokens hashed at rest

The browser gets a 256-bit random token. The database stores only its SHA-256 hash, so a leaked sessions table can't be replayed. Passwords use argon2. The same token works as a cookie or a Bearer header.

Schema evolution

Consolidating two follow systems

The PHP port brought over its own follow_system table (migration 0002), running alongside the newer follows. Two sources of truth for the social graph were a bug waiting to happen, so migration 0005 merged everything onto follows and dropped the legacy table.

Content

One table per attachment type

Images, video, audio, documents, locations and links each have a 1:1 table keyed on post_id. Each type has its own non-null columns, unlike one wide nullable table, and the feed puts them back together with left joins.

Deletion

Soft deletes with partial indexes

Posts and comments set deleted_at instead of disappearing. Rows that point at them stay valid, and partial indexes cover only live rows, so deleted data doesn't slow down normal reads.

Porting

Behavior parity before refactors

PHP idioms that don't map cleanly to Python, such as loose typing and arrays used as objects, are flagged and ported deliberately instead of being "fixed" quietly. Behavior stays identical until a change is chosen on purpose.

07Next

What I'd do next.

  • Denormalized countersLike, comment and share counts come from correlated subqueries for each post. At scale they'd move to counter columns kept up to date in the same transaction as the write.
  • Live notificationsNotifications are written when events happen and read on page load. A Postgres LISTEN/NOTIFY → WebSocket bridge would make them push in real time.
  • Integration testsA pytest suite against a throwaway Postgres covering the privacy rules (pending follows, private profiles), plus enforcing blocks on feed and search reads.
  • Object storageMove media from local disk to S3-compatible storage with signed URLs, so app servers can stay stateless.

08Run it

Local setup in four commands.

Requires Python 3.11+ and a running PostgreSQL. Configuration is read from VP_* environment variables or a .env file.

git clone https://github.com/elite-coder-2026/vantage-point.git && cd vantage-point
python3 -m venv venv && ./venv/bin/pip install -r requirements.txt
createdb vantage_point && for f in migrations/*.sql; do psql -d vantage_point -v ON_ERROR_STOP=1 -f "$f"; done
VP_DATABASE_URL=postgresql:///vantage_point ./venv/bin/python3 -m uvicorn app.main:app --reload
